Why it matters

AI now runs through every part of the business, and every token is billed.

Companies call model APIs from their products, internal tools and agents. Agents and reasoning models multiply the tokens, and a new model comes out almost every month. The question of which model to use never stays answered for long.

The problem, part 1
The developer

Wants the best answer for every task.

And an integration small enough that it doesn’t change how the app behaves.

The problem, part 2
The CFO

Wants spend that is lower, predictable and traceable.

Today: one total bill per provider, spread across separate portals, with no idea which feature or team caused it.

The trade-off

One model for everything forces a trade, on every single request.

Choose a frontier model and you overpay on easy prompts. Choose a cheap one and the hard prompts suffer. Nobody can make that choice by hand, per request.

100×+

The gap in price per token between the most expensive and the cheapest models, and even more at the extremes. Providers also change prices and replace models all the time.

Frontier models

Best on hard reasoning, code and analysis. Priced for it.

Fast, low-cost models

Often just as good on everyday tasks, for a fraction of the price.

How it works

Lönn sends every task to the model that’s good enough, at the lowest cost.

Models are strong at different things. Send each task to the model that handles it best, and a router beats any single model. Here is what happens to one request. (Model names are examples.)

STEP 1

Classify

A small, fast classifier reads the prompt and estimates how likely it is to be each of 15 task types, from arithmetic to legal writing.

About 34 ms per prompt, on a CPU
STEP 2

Score

Every model gets a score based on its measured accuracy and its real billed cost on that kind of task. The choice is based on measured results, not list prices.

score(m) = Σ p(t)·accuracy(t,m) − λ · Σ p(t)·cost(t,m)
STEP 3

Route

The request goes to the best-scoring model in the pool, frontier or low-cost. λ is your dial: lower it for quality-critical features, raise it for simple, high-volume tasks.

A small, carefully chosen pool of models
STEP 4

Check

If the answer comes back empty, cut off, or fails a code example given in the prompt, it would count as wrong. Lönn sends the request once more, to the next-best model, so a broken answer gets a second chance. Then the answer is returned in the format your app already expects.

Integration

Swap one key and one domain. Change nothing else.

  • Use a Lönn API key instead of your provider key, through the API or the Python SDK.
  • Lönn forwards each request to the provider that serves the chosen model and returns the answer.
  • Set the cost-quality balance once, or per call for features that need consistent quality.
client = OpenAI(
- base_url="https://api.openai.com/v1", - api_key=os.environ["OPENAI_API_KEY"], + base_url="https://api.lonnai.com/v1", + api_key=os.environ["LONN_API_KEY"], )

Part 2 · How we validated it

We tested the idea on our own benchmark, with a specific pool of eight models.

Before building the product, we wanted evidence that routing really saves money without losing quality. So we built a prototype router and measured it, prompt by prompt, against every model on its own.

690

Benchmark prompts

Maths, coding, knowledge, instruction following and business writing, from public benchmarks such as MATH-500, HumanEval+, MMLU-Pro, IFEval and WritingBench.

8

Models, strong to cheap

Claude Sonnet 5.5, Gemini 3.8 Flash, Muse Spark 1.3, DeepSeek V4 Pro, DeepSeek V4.1 Flash, GLM 5.3 Flash, gpt-oss-120b and gpt-oss-20b.

5,520

Graded answers

Every model answered every prompt. Each answer was graded with tests, reference answers or a rubric, and its real billed cost recorded, reasoning tokens included.

5×10

Fair testing

Routing decisions were replayed on the stored answers with five-fold cross-validation over ten random splits, so no test prompt ever informed its own routing.
