01 · Definitions / Terminology

Definitions

Accuracy (pass rate)
The share of requests a model answers correctly. In the routing table it is measured per task type and model on the benchmark.
Answer check
A check of a model’s answer before it is returned. It flags answers that are empty, cut off at the token limit, or contain code that fails the examples in the prompt. A flagged answer can trigger one extra call to another model.
API
The interface through which software sends a request to a model provider and receives an answer. Use is billed per call.
Benchmark
A fixed set of prompts with known correct answers or grading rules, used to compare models and routing strategies on the same requests.
Benchmark oracle
A theoretical router that knows every model’s result in advance and picks the cheapest model that answers correctly. An upper bound that cannot be built in practice.
Billed cost
What the provider charges for a request, including input, output and reasoning tokens.
Classifier
The model that estimates which task type a prompt belongs to. In the prototype it is a text embedding (bge-small) followed by a linear layer.
Cross-validation
A way to evaluate on data that was not used to build the router. The prompts are split into folds, and each fold is tested with a routing table built from the others.
Embedding
A numerical vector representation of a text, where texts with similar meaning get similar vectors.
Escalation
Sending a request again to a stronger model after the answer check has flagged the first answer.
Fallback
Sending a request to the next model in the ranking when a provider call fails.
KV cache
Stored intermediate results that let a provider reuse context it has already processed. The benefit can be lost when a request switches model.
LLM judge
A language model that grades another model’s answer against a set of criteria, used where there is no single correct answer.
LLM routing
Choosing, for each request, which model and provider should handle it.
Middleware
Software that sits between the customer’s application and the model providers and forwards requests.
Model pool
The set of candidate models the router can choose between.
Model provider
A company that offers access to a model through an API, for example OpenAI, Anthropic, Google or OpenRouter.
Reasoning tokens
Tokens a model generates while it “thinks” before answering. They are billed as output even though they are often not shown.
SDK
A code library that makes it easier for developers to call a service from their own programs.
Task type
One of the 15 finer categories the classifier uses. Task types are separated where the models perform differently.
Token
A short piece of text, often part of a word, that models read and write. Usage is billed per token, with output usually priced higher than input.
ZDR (zero data retention)
A setting under which the prompt and the answer are not stored after the request has been processed.
02 · Introduction

Introduction

Background

Organisations use AI both through ready-made applications such as ChatGPT and by building large language models into their own products and internal systems through an API. Enterprise spending on generative AI is growing fast, and a large part of it goes to those API integrations.

Enterprise generative AI

$37 billion

Model APIs

$12.5 billion

of that went to foundation model APIs (Menlo Ventures, 2025)

Multi-model use

37%

of 100 surveyed CIOs used five or more models in 2025, up from 29% a year earlier (Andreessen Horowitz, 2025)

  • Billing is per token. Input and output tokens are priced separately, and output usually costs more. The total depends on how many requests are sent, how many tokens each uses and which models handle them.
  • Choosing a model is hard. Public benchmarks help, but a strong score does not guarantee a model suits a particular application. Companies weigh benchmarks against their own testing, cost, reliability, security and existing cloud relationships.
  • The market keeps moving. Providers keep releasing models with different capabilities and prices. Companies buy from several vendors because models differ by use case, yet prompts, guardrails and evaluations become tied to one model, so switching takes engineering and revalidation.
  • Spending is hard to trace. Providers report usage and cost, but not which business activities caused it. Linking spend to teams, features or processes across several providers takes extra integration and maintenance.

Problem

Every AI request has a cost, but not every request needs the same level of capability. Developers need reliable performance, while finance needs to understand and control spending. The problem has two parts.

Part 1

The cost-quality trade-off

An expensive model on a routine task wastes money. A cheaper model on a demanding task can compromise the result. How much is worth paying for the quality each task requires?

Part 2

Traceability

The total bill does not show which features, workflows or customer activities generated it, or whether the quality delivered justified the cost.

Solution

Lönn AI sits between a company’s applications and its AI providers as a single API layer. It handles model selection and makes the resulting spending visible.

  • Routing. Each task goes to a suitable model, based on the quality it requires, the cost of serving it and the company’s security and data-processing requirements. The choices stay aligned as models and prices change, without developers having to monitor the market by hand.
  • Cost tracking. The same layer connects spending to the features, workflows and customer activities behind it. Developers see what their applications cost to run, and finance sees what drives expenditure.

Scope

The pre-study covers organisations that integrate hosted LLMs into their own products and workflows through token-billed APIs, not subscriptions to ready-made chat assistants such as ChatGPT or Microsoft Copilot. It evaluates technical, commercial and regulatory feasibility along two tracks. The intended product and the prototype are not identical.

Track 1 · Theoretical

The intended product

Defines and evaluates the full product from academic literature, provider documentation, participatory design interviews and financial modelling: the routing architecture, expenditure attribution and customer controls, data governance and the commercial model.

Track 2 · Empirical

The prototype

Tests whether automated model selection cuts cost while preserving answer quality. Every tested prompt needs paid API calls, so it is limited to the core routing mechanism, evaluated offline on a fixed benchmark with a limited pool of models.

Cost tracking, billing, data-security enforcement and prompt compression are not implemented in the prototype. They are covered conceptually in the product design and in the roadmap.

03 · Method

Method

Study design

The project was an iterative feasibility study. It identified the technical, business and trust assumptions the service depends on and chose an assessment method for each: prototype development and benchmark testing for routing performance, participatory design interviews and literature review for customer needs and data handling, and a financial model for commercial feasibility.

Findings from one activity informed the next. Stakeholder feedback helped define which routing decisions customers should control, comparisons between prototype versions guided the routing logic, and the measured cost difference between routed and fixed-model requests fed the financial model.

Literature and market review

The literature review focused on three technical questions: whether models answer different requests correctly, whether a router can predict which model to use before an answer is available, and whether new models can be added without retraining the routing system. Results from oracle routing were kept apart from results achieved by implemented routers, because they answer different questions about feasibility.

The market review covered services that route LLM requests through an API, compared by target customers, routing capabilities, customer controls and pricing. For the trust assessment, the team reviewed provider documentation on processing location, retention and training use.

Stakeholder consultations and participatory design

Three participants were consulted. A founding engineer at Zaplar discussed how LLMs were used across product functions, where model selection could be delegated and where predictable quality mattered. An operations specialist with experience of sensitive data advised on retention, hosting, encryption and documentation. A potential customer gave an estimated range of monthly API token usage for a B2B use case, which was used for the customer scenario in the financial analysis.

Prototype development and benchmark evaluation

Benchmark construction

A common benchmark was built so that routing strategies could be compared on the same requests, with a known grade and cost for every model choice. It has 690 prompts across five task families: mathematics (MATH-500), programming (HumanEval+, MBPP+ and LiveCodeBench), knowledge (MMLU-Pro, GPQA Diamond and ARC-Challenge), instruction following (IFEval) and business writing (WritingBench).

Each of the eight candidate models processed every prompt once, producing 5,520 outputs, each stored with its grade and billed cost, including reasoning tokens. Grading followed the task: reference answers, executable tests for programming, rule-based checks for instruction following, and an LLM judge applying the WritingBench rubric for business writing.

Routing

Prompts were grouped into 15 task types. A classifier based on bge-small embeddings and a linear layer estimated the probability p(t) of each task type for a request. For every combination of task type and model, the observed pass rate and mean billed cost per request were calculated. Models were ranked using this score:

Routing score(m) = Σt p(t) · accuracy(t, m) − λ · Σt p(t) · cost(t, m)

Because both terms are weighted by the task probabilities, an uncertain classification gives a smooth decision instead of a hard mistake. λ controls how much weight the router gives to cost; higher values favour cheaper models. The default configuration used λ = 20.

Evaluation

Each routing strategy was evaluated by replaying its decisions against the stored outputs, so versions could be compared without generating new outputs. The final router was evaluated with its output checks enabled and disabled. Five-fold cross-validation at prompt level, repeated across ten random partitions, kept each test prompt’s outcomes out of its routing-table estimates.

The main measures were the overall pass rate across all five task families and total provider cost, including additional calls. The router was compared with the strongest fixed model and with the benchmark oracle, which selects the cheapest model with a passing output for each prompt. Classifier processing time was measured separately on a CPU.

Financial analysis

The financial analysis examined how much of the benchmark saving a customer would keep after service fees, and how much usage Lönn would need to cover its operating costs. Gross savings were the difference between the fixed reference model’s cost and the router’s provider cost for the same prompts. The service fee was applied to those savings, variable costs were deducted, and monthly fixed costs were divided by the resulting contribution to get the break-even spend, expressed as an indicative number of customers. Pricing, customer usage and operating costs were treated as scenario assumptions.

04 · Assumptions and Requirements

Assumptions and Requirements

The pre-study examines three conditions for feasibility. The service must create enough value for customers to justify its fee, select models reliably enough to make routing worthwhile, and handle requests under conditions customers can accept. The assumptions state what must hold for the concept to be viable. The requirements describe what the product must deliver.

4.1

Business

A1 Organisations using LLM APIs have inference costs high enough for routing to give meaningful value, through savings and cost transparency.
A2 Part of that value can be captured through pricing that customers accept and that makes a sustainable, profitable business.

R1 Measurable financial value to customers after service fees.
R2 Visibility into and control over AI spending: usage breakdowns, cost forecasts and routing preferences.
R3 A pricing and payment model that captures a profitable share of the savings while limiting credit risk towards providers.

4.2

Technical

A3 Models in the pool have complementary strengths, predictable enough for per-request selection to beat a single fixed model on cost and quality, and they can be re-estimated as models enter or leave the pool.
A4 The cost and latency added by routing are low enough to keep the benefit.

R4 Lower inference cost at comparable quality and acceptable latency, with minimal integration effort.
R5 Reliable, maintainable routing: automated fallback when providers are unavailable, and modular updates for new models or prices.

4.3

Trust and Safety

A5 Customers will accept standard data-handling settings and documented safeguards as sufficient assurance.
A6 Provider configurations and contracts can be verified well enough to enforce these settings across the eligible pool.

R6 Standard settings for processing location, retention and training use, including zero data retention, enforced across Lönn and downstream providers.
R7 Appropriate security controls, confidentiality and data-processing agreements, current provider information, and documented retention, deletion and incident procedures.

Business. Keeping a product affordable once it gets real traffic is harder than building an affordable prototype, and spending spread over several providers’ portals is easy to lose track of. Capturing the value means taking a share of the savings while customers stay better off; OpenRouter, for comparison, charges a 5.5% platform fee on credit purchases. As a middleman, Lönn must also avoid being left with a provider bill a customer cannot or will not pay.

Technical. The router aims to send simpler requests to lower-cost models and keep more capable models for demanding tasks. Its own processing adds latency and cost, which must be weighed against the savings, and fallback is needed because provider availability varies.

Trust and safety. Lönn matches providers’ published retention and zero-data-retention conditions and verified endpoint configurations against the customer’s settings to decide eligibility, and revalidates them periodically and after relevant changes. ISO/IEC 27001 certification is optional, so the initial approach relies on documented controls, processing agreements and implementation evidence. Customer acceptance of this assurance remains an assumption to validate.

Positioning

Lönn AI should be positioned between the broad model access of platforms such as OpenRouter and the more intelligence-driven routing of companies such as Martian. The aim is not to compete on the number of models and providers, but to choose a sufficiently broad and relevant portfolio and optimise how each request is carried out: better decisions across a diverse and complementary set of models and providers.

Because capabilities, prices and infrastructure costs change quickly, Lönn AI should act as a dynamic optimisation layer that keeps adjusting its routing. Besides lowering cost, this can give customers more stability, since quality stays consistent and spending becomes easier to predict.

06 · Stakeholder

Stakeholders

Customers

A company that uses LLM provider APIs and pays for the tokens, in a product or in internal tools. Leadership or the budget owner (a CTO, head of engineering or IT budget owner) decides and wants lower, more predictable cost with maintained quality. Developers integrate the API and want a small integration that does not change how the application behaves.

LLM providers

The suppliers the product depends on for every request. A pricing change, a limit on access or a new competing feature from a large provider can change the conditions quickly. One reason to use several providers is to reduce this dependence.

Regulators

GDPR and the EU AI Act shape what data can pass through the product and how it can be stored. Where data is processed and whether it is stored affects both the technical design and customer trust.

Competitors

Companies that offer routing and gateways for LLM APIs compete directly for the same customers. Large cloud providers that build routing into their own platforms are part of this group.

Investors

Not engaged at the pre-study stage, but they matter for whether the venture can grow beyond a prototype.

07 · Participatory Design Interviews

Participatory Design Interviews

Product Development

An interview was held with a founding engineer at Zaplar, a Y Combinator startup that builds an agentic hotel system in which several features call LLM APIs. The engineer considered the product highly relevant. The strongest fit was where one agent handles a varied mix of easy and difficult tasks, such as tool calling, natural-language writing, code writing and computational tasks.

The engineer also pointed to a limit: some functions require a fixed level of output quality, where predictable results matter more than lower cost. The customer therefore needs a way to decide how quality and price are balanced. This is reflected in the router’s λ parameter: a function that needs consistent quality can use a low λ, while simpler high-volume tasks can use a higher one.

Trust

The trust and safety approach was developed iteratively with an operations specialist from an AI startup that processes sensitive health-related information. The specialist highlighted working towards the appropriate ISO certification, GDPR compliance, a 30-day retention limit, hosting all data within the EU and encryption at rest. The specialist also helped the team understand the EU AI Act and develop an approach to risk assessment based on probability and impact, and judged that actively working with these factors is adequate to build the trust customers need.

Customer Insight

A person at a potential customer company, who remains anonymous, was consulted on how much usage a typical customer would have through LLM provider APIs. It varies a lot with the product and number of users, but a B2B solution with about 10 users (other companies) would need 100 million to 1,000 million tokens per month.

08 · Result

Result

Evidence from the routing literature

  • Fowler et al. (2026): models were correct on different subsets of tasks. Across 21 LLMs and 16 benchmarks, the oracle scored 88% on average against 82.4% for the strongest fixed model. Matching that model’s score, it cut token costs by 85.2% on average. This supports A3.
  • Ong et al. (2025): RouteLLM, routing between GPT-4 and Mixtral 8x7B, kept 95% of GPT-4’s MT-Bench score at an estimated 73% lower cost. Its most expensive router added at most 0.4% of the cost of GPT-4 generation, which supports A4.
  • Li et al. (2026): on LLMRouterBench, Avengers-Pro reached at least GPT-5’s average accuracy at 31.7% lower cost, or 4.0% higher accuracy in a quality-first configuration. This is direct evidence for R4.
  • Yan et al. (2026): ZeroRouter routes to models outside its original training pool, so the pool can be updated without retraining the whole router.

Proposed product design

Lönn is a middleware between customer applications and model providers. Its design connects customer controls, request routing, and evaluation and improvement.

Customer controls

An API and Python SDK, and a web application with dashboard and settings. The dashboard shows spending forecasts, usage by team, task and model, and estimated savings after service fees. Settings define data-handling policies. Each call can select a saved policy and set the cost-quality balance through lambda.

Request routing

The router selects the most cost-efficient eligible model and provider given lambda. The selected policy and regularly verified endpoint conditions define the execution pool, and fallback follows the same restrictions. Requests fail when no eligible route remains. Prepaid balances or credit limits constrain exposure to unpaid provider charges.

Evaluation and improvement

Authorised retained prompts support clustering and analysis of routing behaviour, following customer permissions. Validation must establish comparable answer quality, acceptable latency and net savings after fees and routing overhead.

Lönn router prototype and performance

The Lönn Router consists of a classifier, a router and an executor. The classifier identifies the likely task type, the router ranks eight candidate models by expected quality and cost according to the customer’s preference, and the executor calls the selected model and records the cost of each attempt. If a provider call fails, the executor tries the next ranked model. If the output is empty, truncated or fails a code example in the prompt, an output check can trigger one additional call.

09 · Discussion

Discussion

Business requirements (R1–R3): partially met

Based on the benchmark, the router delivers clear financial value: at λ = 20 it cuts AI spend by 63.3% after the service fee, for the assumed typical customer. The 20% fee on savings, combined with prepaid usage credits, gives profitability after only 2 assumed typical customers while removing most credit risk. λ gives the customer direct control over the balance between cost and quality, which the Zaplar interview confirmed the need for, and the designed dashboard gives usage breakdowns and a single point of billing across all providers.

The requirements are only partly met because the evidence comes from the benchmark and individual interviews. The savings are calculated for an assumed typical customer, no customer has yet been asked whether they would accept the fee, and the size of the savings depends on the customer’s mix of tasks.

Technical requirements (R4–R5): met on the benchmark

On the benchmark the router keeps about 97% of Claude Sonnet 5.5’s accuracy at about a fifth of its cost at λ = 20 (before the service fee), and at λ = 10 it answers more prompts correctly than Sonnet at about half the cost. The classifier takes 34 ms per prompt on an ordinary CPU, so the router’s own overhead is negligible compared with the savings. This supports A3 and A4 and agrees with RouteLLM and Avengers-Pro.

The prototype falls back to the next model when a provider call fails, and the routing table can be rebuilt when prices change. Adding a new model, however, currently requires running it through the full benchmark, and fallback has not been tested under realistic load.

There are two main reservations. The dataset is limited to 690 prompts with one stored answer per model, and the benchmark consists of exam-style questions, which differ from the prompts customers send. Even so, the difference compared with always using Sonnet is large across the whole range of λ, a strong enough signal that the requirements can be met in practice. Latency for escalated requests, the effect of model switching on caching, and a better pipeline for onboarding new models are left for further work.

Supplier risk

In Lönn AI’s set-up the provider becomes interchangeable, and the customer may not know which model answered. A provider that sees this as a loss of brand recognition or customer relationships can raise prices or restrict access. Anthropic cutting Windsurf’s access to Claude in 2025 (Zeff, 2025), and Anthropic acting as both Cursor’s supplier and competitor (Garfinkle, 2026), show that this happens. A pool spread across several providers reduces the risk, but losing access to the strongest models would lower the value of the whole product.

Trust requirements

The policies and documentation behind the trust and safety requirements have been discussed and planned with the operations specialist, but not developed in practice, so carrying them out becomes a roadmap item. The specialist especially highlighted EU hosting, GDPR compliance, encryption, a 30-day data retention limit and working towards the relevant ISO certification.

Data security also comes as a trade-off against savings. With stricter data-processing requirements, fewer providers are available in the model pool and several of the cheaper models might be excluded. Customers with very strict requirements might therefore get significantly lower savings than the benchmark suggests.

10 · Roadmap

Roadmap

Technical Roadmap

  • Model routing: make it easy to onboard new models without retraining the whole system, with capability vectors learned from observed performance. A small set of shared anchor tasks could support this.
  • Evaluation: broader, representative data and repeatable tests to establish whether routing preserves quality while reducing total cost at acceptable latency.
  • Trust and data handling: customer policies enforced across Lönn and downstream providers, ongoing verification of provider conditions, and implemented security controls and procedures.
  • Reliable execution: provider integrations, failure handling, fallback and monitoring developed and tested under realistic workloads.
  • Customer controls and integration: the API, Python SDK and web application must connect each request with its cost-quality preference and saved data policy.
  • Metering and billing: accurate usage tracking, current provider prices and payment controls, with prepaid balances or credit limits enforced technically.
  • Caching and session memory: assess how model switching affects KV caching and session memory, and count lost caching benefits when estimating savings.
  • Prompt and reasoning optimisation: prompt compression, prompt engineering and reasoning limits as further ways to reduce tokens, validated against answer quality.

Business Roadmap

The business roadmap is a plan of action rather than a schedule. It sets out the order in which Lönn AI moves from a prototype to a product that anyone can use.

  1. Find initial partnersRecruit a small number of companies that rely on LLM APIs in their products, for example AI-heavy startups in Stockholm such as Legora or Lovable, or growing AI startups such as Zaplar. Partners pay only the underlying model costs. In return they share usage data on agreed terms, give feedback and allow Lönn AI to name them as partners.
  2. Run pilotsCollect usage data from real traffic, learn what customers need, verify the product under real conditions and build credibility. Each pilot starts in shadow mode, where the router only records which model it would have chosen, before it gradually takes over real traffic.
  3. Prepare for launchBuild the data and insights from the pilots into the product. Partners move to the standard pricing model and become the first paying customers.
  4. Go liveAny company can create an account, receive a Lönn AI API key and route its requests. Reaching break-even, at roughly two customers, is the first commercial milestone.
  5. Grow after launchUse the partners as references to win similar customers, and the growing usage data to keep improving the router.

Appendix

Disclosure of AI Use

Earlier Iterations

A1. Topic router

The first iterations assumed a router can choose well if it knows what a prompt is about and how hard it is. Laya, an open classifier based on ModernBERT, assigned each prompt to one of four topics and estimated its complexity. Models were scored with public Arena Elo and list prices. Replayed on the benchmark, the topic router reached 78.1% at 1.10 USD. It sent 94% of prompts to one model, DeepSeek V4.1 Flash, and even the true topic of every prompt improved it by only 0.5 points.

Lesson: the routing logic, not the classifier, was the limitation. The complexity score varied too little, four topics were too broad, and list prices predicted actual cost poorly.

A2. Task-type routing and the classifier

With the true task type of every prompt, the new logic matched the topic router’s quality at about a third of the cost (78.9% at 0.40 USD with λ = 80), or gave six points more at lower cost (84.1% at 0.93 USD with λ = 20). The classifier was then chosen by comparison, with a limit of 200 ms per prompt on a CPU. The smallest candidate, bge-small with a linear layer, took 34 ms and brought the router within 0.1 points of the upper bound.

Lesson: once the routing logic was right, the classifier was no longer the bottleneck on the benchmark.

Everyday prompts look little like benchmark questions. On 300 labelled real user prompts from the WildChat dataset, the classifier got 31% of task types right. Adding about 3,000 other WildChat prompts to the training data raised this to 51%.

Lesson: benchmark results are optimistic for real traffic, and data from real use is what improves the classifier most.

A3. Strategies tested against the gap to the oracle

With task types, the router reached 84% against the oracle’s 94%. Of this gap, 68% lies in two task types, algorithmic programming and business writing. Using complexity, requiring two cheap models to agree, and letting a cheap model judge writing were tested and not kept. Checking the answer and escalating at most once was kept; the report finds it equal or better at every budget, by up to 1.9 points.

The full spreadsheet model is in the report. Its case customer uses 500 million tokens per month, which would cost 2,000 USD per month on Claude Sonnet 5.5 and 417 USD per month through the router, before the service fee.
